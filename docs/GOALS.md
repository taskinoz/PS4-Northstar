# Goals & next steps

This is the entry point for planning work on the PS4 Northstar port. It replaces the old "Stage 1 / Stage 2" narrative framing: Goal 0 (formerly "Stage 1") is complete, and everything since has been native runtime work (formerly "Stage 2"). The goal list below is the current source of truth for status; [TECHNICAL-NOTES.md](TECHNICAL-NOTES.md) is the detailed, chronological lab notebook (exact hashes, virtual addresses, byte preimages, run IDs) behind it.

## How to use this document

Each goal is scoped so it can be handed to a single agent/session on its own: it states the objective, current status, what is already verified, and what specifically remains. Before touching any hash-locked binary (`eboot.bin`, `engine.prx`, `client.prx`, ...), read the **Safety rules** section at the bottom — they apply to every goal below without exception.

Status legend: ✅ complete · ⏳ in progress · ⬜ not started

## Goal 0 — Foundation: static content integration ✅ complete

Get Titanfall 2 on PS4 (via shadPS4) to connect to a Northstar server by IP, using only static PS4 VPK patches — no native runtime code. Full detail in [FOUNDATION.md](FOUNDATION.md).

**Still required, not obsolete:** the currently-installed game boots on top of these patched VPKs and the UI-compatibility transforms in `scripts/Apply-Stage1Compatibility.ps1`. Keep this tooling until the native equivalents (Goals 3, 6, 7) cover everything it currently papers over — see "Retiring the Goal 0 VPK patches" under Next steps.

## Goal 1 — Native PRX bootstrap ✅ complete

Load `northstar_ps4.prx` before Titanfall's own game modules via a hash-locked `eboot.bin` patch, execute its initializer, and return control cleanly to normal boot. Verified under shadPS4; the game reaches the main menu with the PRX loaded.

## Goal 2 — Runtime module discovery ✅ complete

Resolve `engine.sprx` / `client.sprx` handles and segment mappings at runtime using the OpenOrbis module-info API, with no fixed/hard-coded addresses (shadPS4 base addresses are per-run and must never be hard-coded).

## Goal 3 — Native ConVar registration ✅ complete

Statically profiled the engine's internal ConVar constructor path for the exact retail hash (`config/stage2-offsets-CUSA04013.json`) and registered two ConVars through it at runtime: a diagnostic (`ns_stage2_loaded`) and `ns_allow_team_change`. Both verified via `FindVar` returning the exact object the PRX allocated. (Originally registered as `ns_allow_team_changes`, plural — corrected 2026-08-07 to the singular spelling the shipped UI scripts actually use; see Goal 8 below.)

## Goal 4 — Native Squirrel function registration ✅ complete (proof only)

Registered a callable native (`NSStage2Ping`) into the UI Squirrel VM's real global table and had a shipped UI script call it successfully (`NSStage2Ping invoked` in the log). The sparse-script edit used for the proof was reverted afterward; the mechanism itself — insert into `internal+0x40d0`, never the type-registry table at `+0x4120` — is documented in [TECHNICAL-NOTES.md](TECHNICAL-NOTES.md) and ready to reuse.

## Goal 5 — Filesystem overlay + mod metadata discovery ✅ complete

- PC Northstar mod loose files (`Northstar.Client`, `Northstar.Custom`) are served from the PS4 `r2` search directory with zero VPK repacking and no engine memory mutation.
- The native PRX discovers mods from `/app0/mods` at runtime, parses each `mod.json` with a self-contained parser, and registers every mod ConVar through the Goal 3 constructor (18/18 verified in the last run).

## Goal 6 — Runtime mod script loading ⏳ in progress

- [x] Discover each mod's `Scripts` array from `mod.json` (parsed and counted; not yet compiled).
- [x] Compile an arbitrary script file into the engine at runtime via `CompileList` (client VA `0x3153f0`). A crash in this path was root-caused and fixed on 2026-08-07 (see TECHNICAL-NOTES.md) and is now verified 3/3 with no crash.
- [x] Determined the `scripts.rson` manifest-overlay approach (`Merge-Stage2ScriptsRson.ps1`) does **not** work: the engine reads the VPK-packed vanilla `scripts.rson`, not the `r2`-staged merged copy, whenever the same path exists in both. `CompileList` is the correct mechanism going forward, not the manifest merge.
- [x] Drive `CompileList` from each mod's already-parsed `Scripts` array instead of the one hardcoded probe path used to prove the mechanism. `ModInfo` now stores each mod's `RunOn: "UI"` script paths; collection into a shared buffer always runs (harmless) when mod metadata + script inject are both enabled. **Actually compiling that real list crashes** on at least one real script (`ui/menu_ns_modmenu.nut`, a real-address fault reading `internal_vm+0x40a0` — see TECHNICAL-NOTES.md), so it's gated behind a further opt-in flag (`-EnableM6ScriptInjectFromMods`) that defaults off; the safe combined build falls back to the harmless probe file and was re-verified clean. The table itself was profiled and found healthy on a normal boot — see next item, the crash is not simply "table unpopulated."
- [ ] Prove a runtime-compiled script's code actually *executes*, not just compiles. Blocked: bare top-level statements don't compile in this UI script compiler, and `FindUiFunction` does not reliably resolve names (see Next steps below for the concrete unblock).
- [x] Profiled `internal_vm+0x40a0` — it's healthy, not the blocker (see below).
- [ ] **Refined (2026-08-07, live-debugged with cdb — see "Debugger setup" and "Live crash analysis" in TECHNICAL-NOTES.md):** `internal_vm+0x40a0` is *not* broadly unpopulated — a debugger attached to the actual fault confirmed `rbx` (the table read) is exactly null (`ds:...038`, i.e. `0+0x38`), but a breakpoint just before the crash showed the *same* table healthy and stable across at least 6 preceding calls in the same compile, with a counter (`internal_vm+0x40c0`) incrementing each call. The miss happens on one *specific, later* call — most likely resolving `ModInfo` itself — not because the table doesn't exist. Next: a conditional breakpoint (`rbx == 0`) to land exactly on the failing call; recipe drafted but untested in TECHNICAL-NOTES.md. Still gated behind `-EnableM6ScriptInjectFromMods` (default off).

## Goal 8 — Real server connectivity & Atlas authentication ⬜ not started

**Re-scoped 2026-08-07.** Full Atlas authentication needs the game's own signed license/session token (tied to the real PSN/game account) — sensitive, and not a near-term priority. De-prioritized; revisit only if a path is found that doesn't require handling that token directly (`tools/NorthstarLauncher-reference` has the PC reference implementation if that's ever attempted — treat as research-first, do not touch `engine.prx`/`client.prx` before the research is written down).

The practical near-term path is **unauthenticated connectivity**: `ns_auth_allow_insecure` is a *server-side* ConVar (`ServerAuthenticationManager::CheckAuthentication`/`AuthenticatePlayer`,`tools/NorthstarLauncher-reference/primedev/server/auth/serverauthentication.cpp`) that makes a server accept connecting players without validating any Atlas token. Because it's entirely server-side, the PS4 client likely needs **no** Atlas-specific work at all to connect to such a server — Goal 0's existing direct-connect flow may already be sufficient (its success criteria already claim a controlled Northstar server connects cleanly). This hasn't been tested end-to-end since the native runtime work began, and doing so would also be the first real opportunity to verify several other currently-open items live (Goal 6 script execution, `ns_allow_team_change` gameplay effect, general stability under real play) — see Immediate next steps.

## Goal 11 — Native mod localisation loading ✅ complete (probe verified)

Native mod `Localisation[]` loading through the game's own localize.prx `AddFile` (VA `0x5c60`). The singleton object lives at `localize base + 0x1d280`; its vptr (installed by module init) points to the relocated rodata vtable at `base + 0x18010`, whose slot 9 (`+0x48`) is `AddFile` itself. Verified 2026-08-14 (run `work/stage2/iterations/20260814-163721`): the stock deployed mods' `Localisation[]` entries (`resource/northstar_client_localisation_%language%.txt`, `resource/northstar_custom_%language%.txt`) both loaded with `result=1`, plus a vanilla-english self-test `result=1` — `files=2 loaded=2`, clean boot. Full ABI details, the `this+0x48` fallback-field forcing, and the module-segment-extent fix are in TECHNICAL-NOTES.md. Gated behind `-EnableM6Localise` + `-EnableM6ModMetadata` (off in the default inert build).

## Goal 12 — Real Northstar mod compile list + hook dispatch ✅ complete for Northstar.Client (2026-08-15)

**This is the actual "PS4 Northstar launcher loads real PC mods, not hand-patched copies" milestone**, requested directly by the user: retire the hand-merged/hand-patched Northstar.Client copy Goal 0 originally baked into the VPK, and replace it with the genuine, unmodified mod pulled straight from the user's PC Northstar install (`config/local.json`'s `northstarModsRoot`).

Two structural discoveries made this possible:
- **`scripts.rson` is the real, content-editable UI/CLIENT/SERVER script compile list** — not a native/hardcoded one as an earlier session wrongly concluded (see the Goal 8-era `menu_direct_connect.nut` saga in TECHNICAL-NOTES.md). It's one file, resident in the frontend VPK, shared across all three VPK targets' script content.
- **A modified `scripts.rson` only takes effect if it's baked into the VPK** (`work/stage1/sparse`), not staged into the r2 loose-file overlay — the engine reads the VPK-packed one whenever the same path exists in both (already known from the earlier `Merge-Stage2ScriptsRson.ps1` dead end, just not previously connected to this fix).

New tool: `scripts/Build-Stage1ModIntegration.ps1`. For each selected mod, it reads the *real* `mod.json`, stages only the exact files it declares (`Scripts[]`, `InitScript`, `Localisation[]` — never a wholesale directory copy, see the hard lesson below), bakes a merged `scripts.rson`, and generates a `UICallback.Before`/`After` hook-dispatch block inserted into `_menus.nut`'s `InitMenus()` between `// === PS4_MOD_HOOKS_BEFORE/AFTER_START/END ===` markers — substituting for NorthstarLauncher's native hook dispatch, which has no equivalent on this port. Regenerating is idempotent; do not hand-edit the marker block or the compatibility patches will fight it.

**Hard lesson (real damage, recovered from the deployed VPK via `tf2vpk-bin`, not git — `work/stage1/sparse` isn't tracked):** the first version of this script mirrored each mod's whole `mod/` directory. Real PC Northstar mods routinely ship their own copies of core files (`panel_mainmenu.nut`, `_menus.nut`, `menu_main.nut`, ...) as PC-only r2-overlay content overrides. A wholesale copy silently overwrote this port's PS4-specific patches to those exact files with pristine PC content — no error, `Copy-Item -Force` just wins. Fixed: the script now stages *only* the exact paths a mod's `mod.json` declares, nothing else. Where a real mod's declared file genuinely needs a PS4-specific delta (see `_custom_codecallbacks_client.gnut` below), the fix lives in `Northstar.PS4` (`LoadPriority: 99`, staged last, wins the file-copy collision) as a full copy of the real file plus the addition — never a hand-edit of the real mod's own copy, which the next integration run would silently discard.

**Northstar.Client: 13 of 21 real UI/CLIENT scripts wired in and verified booting clean** (full stdout capture, no `FatalError`, both ConVars registered, stable 3+ minutes at the main menu). Chat, Discord-presence hooks (stubbed, see below), the mod-settings-per-mod UI, the color picker, controller prompts, mouse capture, and `Northstar.DirectConnect` all compile and their `UICallback.Before` hooks fire for real. Eight distinct real issues found and resolved live, in order:

1. `menu_ns_color_picker.nut`'s `RunOn: "UI || CLIENT"` was staged to both `frontend` and `mp_common` targets, each emitting its own `scripts.rson` block — but both land in the *same* file, so the engine saw it listed twice (`FatalError: ... is being loaded more than once`). Fixed: dedupe scripts.rson entries by `RunOn|path`, not `target|RunOn|path`.
2. `InitScript` (`cl_northstar_client_init.nut`, defines `global struct ModInfo`) was only compiled into the `CLIENT` VM, but `menu_ns_modmenu.nut` (`UI` VM) uses `ModInfo` as a type — Squirrel VMs per context don't share a global table. Fixed: `InitScript` now compiles into `UI || CLIENT`.
3. Even fixed for the right VM, `InitScript`'s block was being appended *after* the mod's other `Scripts[]` entries in the merged file — but a struct type must be compiled before anything that uses it as a type annotation (no forward declaration for struct types, unlike `global function`). Fixed: `InitScript` is now emitted first, before the mod's own `Scripts[]` loop.
4. `presence/ui_presence.nut`'s `UICallback.After` (`NSUpdateGameStateUIStart`) and `presence/cl_presence.nut`'s `ClientCallback.After` (`NSUpdateGameStateClientStart`) are both undefined anywhere in Northstar.Client's own scripts — confirmed by the user to be a separate Discord Rich Presence **plugin DLL**, not core Northstar, so there's no PS4 equivalent to build at all. Stubbed permanently as no-ops via `Northstar.PS4` (`ui/ns_ps4_presence_stub.nut`).
5. `menu_ns_modmenu.nut` (in-game mod list: enable/disable, reload) needs `NSSetModEnabled`/`NSGetModsInformation`/`NSReloadMods`/`NSGetModInformation` — real native mod-management functions this port doesn't implement (Goal 7). Deferred (excluded from the compile list) rather than stubbed with fake data.
6. `menu_ns_moddownload.nut` (downloading mods from a repository) needs `NSDownloadMod`/`NSCancelModDownload`/`NSFetchVerifiedModsManifesto`/`NSGetModInstallState` — same category, plus an online mod repository this port has no plan for at all. Deferred.
7. `menu_ns_setversionlabel.nut` (cosmetic version label) needs `NSGetModInformation` (see #5) plus `NS_VERSION_*` native constants. Deferred.
8. `menu_ns_serverbrowser.nut`: needs the native masterserver client (see Goal 13) for its actual server-list functions, but *also* has its own unrelated compile error — `FatalError: ... wrong number of parameters (calling unknown function): found 5, expected 4` — not yet root-caused despite substantial static-analysis effort (no line number in the error, and every 5-argument call site found by hand or by script was verified to match its real signature). Deferred; revisit with live debugging (cdb) when implementing Goal 13, in the same file, with full context.
9. `menu_ns_connect_password.nut` depends on `menu_ns_serverbrowser.nut`'s `OnServerSelected_Threaded` — cascades from #8, deferred too.
10. `menu_ns_custom_match_settings.nut` / `menu_ns_custom_match_settings_categories.nut` need `GetPrivateMatchSettingCategories`/`GetPrivateMatchCustomSettingsForCategory` — the exact "CustomServers API" category `Apply-Stage1Compatibility.ps1` already strips from `menu_private_match.nut` for the identical reason. Deferred.
11. `atlas_auth.nut` needs `NSIsMasterServerAuthenticated` and the rest of the Atlas auth native surface (Goal 13). Deferred.

The full working exclusion list is the default value of `Build-Stage1ModIntegration.ps1 -ExcludeScripts` — re-run with a shorter list to re-attempt any of these once their native dependency exists; each is documented inline in the script with exactly what it needs.

**Also fixed as part of this:** the main menu's "Launch Northstar" button used to unconditionally unlock and open `DirectConnectMenu` — identical to the standalone "Direct Connect" button next to it (reported live: "the launch northstar button goes to the direct connect menu as well as the direct menu button"). It now stays locked (its real default state) until it has something genuine to open — the server browser, once Goal 13 lands.

**Not done, tracked separately:** `Northstar.Custom` (weapons/gamemodes, 65 `Scripts[]` entries) — see the new task for it; it needs `ServerCallback`/`ClientCallback` hook dispatch (this milestone only built `UICallback` dispatch) and a wider `RunOn` expression parser, and most of its content can't be meaningfully tested until a live match works at all (still blocked on the network-handshake-stall issue below).

## Goal 13 — Native Atlas masterserver client ⬜ not started

Real Northstar server browsing and Atlas authentication both route through a set of native Squirrel functions (`NSRequestServerList`, `NSGetGameServers`, `NSGetServerCount`, `NSTryAuthWithServer`, `NSIsMasterServerAuthenticated`, `NSConnectToAuthedServer`, and others — see `tools/NorthstarLauncher-reference/primedev/{masterserver/masterserver.cpp,scripts/client/scriptserverbrowser.cpp}` for the full real implementation) that don't exist on this port at all. Implementing them needs a real native HTTP client (shadPS4 already HLEs `sceHttp*` for the game's own background chat/np activity, so the capability exists at the platform level) plus JSON parsing, following this project's existing hash-locked, preimage-gated native-registration conventions (see `launcher/src/runtime.cpp`'s `NSStage2Ping` proof-of-concept for the pattern — note that `array<ServerInfo>` return marshaling is a materially harder case than that simple `void()` example, and this work directly touches hash-locked engine memory, so treat it with the same care as any other native milestone: read-only proof first, validate preimages, don't skip the incremental verification steps).

**A local, self-hosted Atlas instance is already running and verified working**, specifically for developing and testing this goal without needing real EA/Origin credentials:
- Source: `tools/Atlas-reference` (cloned from `https://github.com/R2Northstar/Atlas`, Go project, `go build ./cmd/atlas`).
- Launched with `ATLAS_API0_INSECURE_DEV_NO_CHECK_PLAYER_AUTH=true` — a genuine, officially-supported config flag (`pkg/atlas/config.go`) that skips the real Stryder/EA origin-token validation step entirely (`pkg/api/api0/client.go`, gates the `stryder.NucleusAuth` call and the per-server/self auth-token checks). Confirmed: the initial origin-login step accepts an empty/placeholder token in this mode.
- Listens on `:8080` by default (plain HTTP, no TLS config needed) with in-memory storage (`ATLAS_API0_STORAGE_ACCOUNTS=memory`, `ATLAS_API0_STORAGE_PDATA=memory:compress` — both defaults, no persistence needed for testing).
- Verified live: `curl http://127.0.0.1:8080/client/servers` returns a valid `[]` — the exact response shape `MasterServerManager::RequestServerList()`'s real C++ implementation expects (a plain GET to `{hostname}/client/servers`, no auth header/param at all — server list fetching needs no token, only per-server auth (`NSTryAuthWithServer`) does).
- The PS4 client's `ns_masterserver_hostname` (`work/stage1/sparse/frontend/cfg/autoexec_ns_client.cfg`) is already pointed at it (`http://192.168.0.126:8080`, this machine's LAN IP — update if the Atlas instance moves).
- **The user's separate dedicated Titanfall2 server also needs to point at this same Atlas instance** for it to register and actually show up in a server list once the client-side native work exists — not yet done/confirmed as of this note.

- Real PS4 kernel/module-list behavior may differ from shadPS4 in ways that break Goal 2's discovery logic; it has never been tested outside the emulator.
- `CompileList`'s internal object/vtable dependency (Goal 6) was observed populated in 3/3 recent runs but null in one earlier run; the exact readiness condition is still not fully understood, only safely gated against.
- The `ns_allow_team_change` ConVar's semantics (`default=0 flags=0`) were chosen conservatively because current upstream Northstar no longer defines this legacy identifier under either spelling — verify this is still the right default before shipping anything that depends on it.
- No investigation has started on whether the server browser is reachable from a PS4 client's network stack under shadPS4; direct-connect (Goal 0) is the only tested connectivity path so far.
- Compiling a real mod UI script with a typed struct parameter (`ui/menu_ns_modmenu.nut`, using `ModInfo`) via `CompileList` crashes reading `internal_vm+0x40a0`. Live-debugged (2026-08-07): the table itself is healthy and stable across multiple calls in the same compile; the null happens on one specific, later call, most likely resolving `ModInfo` itself. Root cause (why that one lookup misses) still open. Not all mod scripts are necessarily affected — only one has been tested — but treat any `-EnableM6ScriptInjectFromMods` script as unverified. See TECHNICAL-NOTES.md.
- `ns_auth_allow_insecure` is a server-side setting (confirmed by reading `tools/NorthstarLauncher-reference`'s source) — connecting to an insecure server should need no PS4-side Atlas work. **Now confirmed against a real connection attempt (2026-08-17, see TECHNICAL-NOTES.md "Real dedicated-server log: root cause of the connect-then-freeze report"): the reported freeze was not a client-side stall at all.** The dedicated server's own log shows the player fully connecting, spawning, and playing the dropship intro, then ~11s later getting kicked with `connection was rejected: "Authentication Failed."` (from `serverauthentication.cpp`'s `CheckAuthentication`, which only ever produces that message when `Cvar_ns_auth_allow_insecure->GetBool()` is false at that moment). Since the user toggled `ns_auth_allow_insecure` and still got rejected either way, the convar was almost certainly being set somewhere other than the dedicated server's own console/cfg (it's an `FCVAR_GAMEDLL` cvar read only by the server process — setting it PS4-client-side has no effect on this check at all). **Action for the user: set `ns_auth_allow_insecure 1` directly in the dedicated PC server's own config/console (not the PS4 client) and restart it**, since this port's native Atlas client (Goal 13) doesn't exist yet to supply a real per-connection auth token.
- **A live connection to a real dedicated server used to stall after entering level load, with no error** (client threads observed idle via cdb, 2026-08-08). Superseded by the finding above: the 2026-08-17 server log shows the client now gets much further (full spawn + intro) before the real blocker (server-side auth rejection) hits, so this may have already been resolved by other fixes since 2026-08-08, or may resurface once the auth rejection above is worked around — not yet re-tested in isolation.
- **`scripts.rson` merge insertion-order bug, found and fixed 2026-08-17:** `Build-Stage1ModIntegration.ps1` used to insert all mod-provided `scripts.rson` blocks immediately before the vanilla `// DEVSCRIPTS CONTENT` marker, near the very end of the file. Vanilla content much earlier in the file (e.g. `sh_damage_types.nut`, ~line 191) can reference mod-provided globals (e.g. `AddServerToClientStringCommandCallback`), and Squirrel has no forward declaration for not-yet-compiled globals — this produced an intermittent `FatalError: ... CLIENT SCRIPT COMPILE ERROR: Undefined variable "AddServerToClientStringCommandCallback"` even though the stub was correctly staged and present in the deployed VPK. Fixed: mod blocks are now inserted right after the header comment, before the *first* vanilla `When:` block, so all mod content compiles before any vanilla content that might depend on it. Verified in the redeployed VPK: `_custom_codecallbacks_client.gnut` now appears at line 82, `sh_damage_types.nut` at line 269.
- **Generic dialog UI (`OpenDialog`/`AddDialogButton`, `menu_dialog.nut`) does not respond to any input** (keyboard, mouse, controller, or the native `toggleconsole` bind) — confirmed live 2026-08-07 on `NorthstarMasterServerAuthDialog`. All the underlying script/resource files (`menu_dialog.nut`, `_menus.nut`, `dialog.menu`) are byte-identical to unmodified retail content and already have correct `tabPosition`/`navUp`/`navDown` wiring, so this isn't a simple script-data fix. Root cause not yet found — needs live cdb investigation into whether the engine's native `FocusDefaultMenuItem`/input-polling functions are even being reached, or whether shadPS4's pad/keyboard HLE layer is delivering events at all. Currently worked around for the auth dialog only by pre-agreeing `ns_has_agreed_to_send_token` (see item 1) — but this will block **any other dialog** the player reaches (leave-match confirm, error dialogs, data-center picker, etc.), so it needs a real fix before those become reachable in testing.

## Safety rules (always apply)

- Never reuse NorthstarLauncher's Windows `engine.dll`/`client.dll` offsets on PS4 — every address here is PS4-binary-specific.
- Key every code patch to a retail module hash and an exact byte preimage; validate both at runtime before dereferencing anything.
- Keep generated game data, extracted VPK content, retail binaries, and toolchain archives out of Git (see `.gitignore` and `tools/README.md`).
- Back up before replacing any file in the game directory; keep the `eboot.bin` rollback path working.
- Treat shadPS4 behavior and real PS4 behavior as related but distinct targets.
- Make the next native milestone read-only until module identity and base addresses are verified, and restore the default inert PRX with a clean-boot check after any experiment.
