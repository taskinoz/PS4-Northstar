## Current direction — 2026-09-06

Earlier Stage 1 successes prove only the historical patched-content setup; they do not prove a native-only loader works.

## Acceptance target: PC parity except authentication

The user explicitly requested 1:1 Northstar behavior except authentication. Authentication is intentionally disabled; no fabricated success/tokens are permitted. Downloads, server-list transport, assets/KeyValues, mod enable/reload, full VM lifecycle and script APIs are still required work, not additional allowed exclusions. Current offline adapters and restart-required reload behavior do not meet parity. Do not present the development installer as a completed Northstar port.

Installation instructions are in `docs/INSTALL.md`. Builds now produce a hash-bound feature record; `Get-NorthstarInstallStatus.ps1` identifies the installed runtime without interpreting mod-folder presence as execution.

New mods default enabled. Missing metadata versions default to `0.0.0`, matching the checked-in PC reference.
- Filesystem overrides, ConVars, localisation and the experimental UI script collector all use the filtered, sorted discovery list under `/app0/R2Northstar/mods`. Higher-priority loose files win. Metadata/discovery support is enabled automatically with the filesystem build flag.
- Packaging discovers mod folders without a hard-coded mod selection manifest, verifies unchanged copies, preserves enabled settings and never touches game archives or flattens files into `r2`.
- VPK modification and script-merge entry points fail before writing. Existing modified installations are not automatically restored.

The clean-VPK native loading probe below now verifies filesystem coverage and manifest compilation. Full Northstar UI startup remains unimplemented; historical patched-content proofs do not establish it.

## Safe I/O, JSON and UI lifecycle - 2026-09-17

- **The UI script VM now completes Northstar's full startup on PS4.** UI compilation finishes, InitScripts compile at VM creation, and every Before/UIInit/After callback runs in enabled-mod load order: `AddNorthstarModMenu`, `AddNorthstarServerBrowserMenu`, `AddNorthstarConnectWithPasswordMenu`, `AddNorthstarCustomMatchSettingsCategoryMenu`, `AddNorthstarCustomMatchSettingsMenu`, `AddModSettingsMenu`, `NSClientModSettings`, `Progression_Init`, `Testing_Init`, `NSCustomModSettings`, then `AddNorthstarModMenu_MainMenuFooter`, `NS_SetVersionLabel`, `NSUpdateGameStateUIStart`, `AddColorPickerMenu`, `AtlasAuthDialog`, `InitialiseArenaLoadouts`.
- Callback dispatch now matches PC exactly: a mod callback's return value is ignored and the remaining callbacks still run. `NSUpdateGameStateUIStart` is declared in Northstar.Client's `mod.json` but defined in no installed script, so it is logged as missing and skipped, which is what PC does. Previously the PS4 dispatch aborted the chain there and never reached the last three callbacks.
- Added the Safe I/O family (`launcher/src/runtime_save_files.inl`): `NSSaveFile`, `NSSaveJSONFile`, `NS_InternalLoadFile`, `NS_InternalGetAllFiles`, `NSDoesFileExist`, `NSGetFileSize`, `NSDeleteFile`, `NSIsFolder`, `NSGetTotalSpaceRemaining`. Per-mod isolation is real, not shared: `CallingSource` reads the PS4 VM call stack (`sqvm+0x38/0x40`, CallInfo stride `0x48`, `OT_FUNCPROTO` at `ci+0x20`, source `SQString` at proto+0x40, characters at +0x30 - the layout the client's own callstack printer uses at VA 0x67f062-0x67f0bf) and resolves that script to its owning mod through the same priority-ordered mod roots the filesystem hook serves, reproducing PC's `getcallingmod` + `m_ModFiles` lookup. Storage is `/data/northstar_ps4/save_data/<mod folder>`.
- Save policy is enforced in a portable, host-tested header (`launcher/include/northstar_ps4/mod_savefiles.h`): ASCII-only relative paths that cannot escape the mod folder, the PC `.txt`/`.json` write whitelist, NUL rejection and PC's 50 MiB advisory folder cap. Writes are atomic (temp file, fsync, rename) and a failed write preserves the previous file.
- Added `DecodeJSON`, `EncodeJSON` and `NSSaveJSONFile` (`launcher/src/runtime_json.inl` with a portable parser in `launcher/include/northstar_ps4/json_text.h`). PC uses RapidJSON; PS4 has none, so the text parse, escaping and number classification (whole numbers become Squirrel integers, everything else floats; values outside 32-bit stay floats rather than wrapping) live in a host-tested header. Squirrel values are built through profiled engine primitives - `sq_newtable` (0x683230), the table insert already gated for constants (0x6ab3e0) and string interning (0x6a96a0) - with the engine's own refcount protocol. `EncodeJSON` reads `SQTable`/`SQArray` directly (`table+0x38` nodes, `+0x40` count, node stride 0x28; `array+0x30` values, `+0x38` used), skipping types PC also cannot represent.
- Load results reach `NSHandleLoadResult` through a deferred queue and a real argument-passing script call: function lookup (0x685cf0), object push (0x6875f0), the VM root table at `sqvm+0xb8` and `sq_call` (0x6876c0), followed by the closure pop the engine performs. **This queue is not drained per frame.** PC drains it from `CHostState::FrameUpdate`; no equivalent PS4 per-frame hook is profiled yet, so a result is delivered at the next UI code callback. No installed mod calls `NSLoadFile` during menu startup, so this path is implemented but not yet exercised by real content.
- Every new engine entry point is gated on an exact byte preimage before use, alongside the existing gates. The controlled boot passed all of them.
- Latest boot: `work/stage2/iterations/20260917-134347/shad-new-lines.log`; experimental PRX SHA256 `830102e32f74b0a3fb8d74415ab595137486ec95b8dbd5eb9518ddee897a78f2`. Status `success` on `UI lifecycle completed`.
- The only parse errors in that boot come from the mod's own content, not the loader: `resource/ui/menus/colorsliders.menu` is served correctly from `Northstar.Client`, but the file ends with an XML-style `<!-- ... -->` comment around its `DialogFooterButtons` block, which Source KeyValues does not support (`got } in key`, `missing {`). PC hits the same thing. Every other `Northstar.Client` `.menu` resource parsed without error. Mod sources are not edited to work around this.
- Authentication, the server browser, mod downloads and Atlas transport remain deliberately unimplemented and continue to return explicit unavailable states.

## CLIENT VM lifecycle - 2026-09-17

- The lifecycle code is now context-generic. `RuntimeVmInit` sets up whichever context the engine creates (1 CLIENT, 2 UI): constants, context-filtered native registration, InitScript compilation and InitScriptCallback dispatch. A missing InitScriptCallback is now logged and skipped rather than failing the VM, matching PC.
- `ClientCodeCallback_MapSpawn` (VA 0x768386) is hooked for CLIENT Before/After dispatch, alongside the existing UI hook. These are exactly the two callback names PC's `bShouldCallCustomCallbacks` allows custom callbacks for. The CLIENT VM teardown at VA 0x2e7813 joins the three UI teardown paths in one destroy hook that matches the owner against each context's state.
- Natives now carry PC's `ADD_SQFUNC` context masks, and each context gets its own registration records. New natives: the CLIENT chat family (`NSChatWrite`, `NSChatWriteLine`, `NSChatWriteRaw`, `NSSendMessage`) plus `StringToAsset`, `NSGetCurrentModName` and `NSGetCallingModName`. `StringToAsset` and the two mod-name natives are real implementations (`sq_pushasset` at 0x682f40, and the existing call-stack mod resolution). **The four chat natives are logged adapters that neither render nor transmit** - PC routes them through `LocalChatWriter` and engine.dll's `ClientSayText`, neither of which is ported. They exist because their absence was the documented cause of the earlier "frozen on connect" report, and they replace the retired `Northstar.PS4` script stubs with native adapters so no mod source is edited.
- Pending Safe I/O load results are now keyed to the VM that requested them, so a CLIENT load cannot resolve into the UI VM, and a closing VM drops its undelivered results.
- **Build constraint found the hard way:** this module's `DT_INIT` is patched to call the module initializer directly, which bypasses the crt walk of `.init_array`, so **no C++ dynamic initializer runs**. A global whose initializer is dynamic rather than constant is silently left zero-filled. See [TECHNICAL-NOTES.md](TECHNICAL-NOTES.md) for the crash this produced and the rule it implies for every global in this module.
- Boot `work/stage2/iterations/20260917-142801/shad-new-lines.log`, PRX SHA256 `829a4f59b082760fd8d4e331a920f89c4ebbbed4e3d95e0e426e39308496cbaa`: both hooks installed with page protection restored, 15 UI and 27 CLIENT callback entries loaded, UI startup unchanged and still reaching `UI lifecycle completed`. All 1,069 recorded VPK/mod files unchanged; host tests and both builds pass.
- **KeyValues patches: discovery works, the merge does not (2026-09-17).** `launcher/src/runtime_keyvalues.inl` finds all 9 patches the installed mods ship (the playlist, font table, an AI settings file, five weapon files) - none of which were ever applied. Reproducing PC's approach of generating a `#base` wrapper **fails on this engine**: it reads the wrapper and never opens a single `#base` target, so the empty root object yields `FatalError: Failed to load playlist data` and no main menu. Serving is therefore disabled (`kKeyValuesServeGenerated = false`) and behaviour matches pre-feature; boot verified to the real main menu. The merge must instead be performed by this module into one complete file, which needs a KeyValues parser and Northstar's precedence rules. Discovery, patch enumeration, original retrieval and root-name parsing are correct and reusable.
- **`#base` is supported, but not by the playlist loader (2026-09-17).** 231 vanilla files rely on it - 128 in `scripts/aisettings`, 69 in `scripts/players/mp`, 17 in `resource/ui/menus`, 14 in `scripts/weapons` - so those loaders process it. **No vanilla playlist uses it**, and the engine ignored it in the generated wrapper. Of the nine mod patches, seven (`scripts/weapons/*`, `scripts/aisettings/*`) could use the cheap `#base` route; `playlists_v2.txt`, the one gating every custom gamemode, cannot and needs a real in-module merge.
- **Every custom-gamemode failure has one cause: KeyValues patches are not implemented (2026-09-17).** `Northstar.Custom/keyvalues/playlists_v2.txt` defines `fastball`, `gg`, `arena`, `chamber` and the rest, and is **never read** - KeyValues patches live in `<mod>/keyvalues`, a sibling of the `<mod>/mod` overlay roots, and PC merges them via generated `#base` wrappers (`ModManager::TryBuildKeyValues`) rather than serving them directly. The client therefore runs the stock playlist while the server runs a merged one. This accounts for the missing fastball icon, the odd Modes menu, custom-mode matches connecting but never entering the game, and the custom-mode out-of-sync - while attrition and TDM work because they are in the stock playlist. The client *does* receive the server's gamemode (`GAMETYPE: aitdm`), so that earlier hypothesis is dead. Fix has a precedent: `BuildRuntimeManifest` already generates and serves a merged `scripts.rson` the same way.
- **Script output is now visible (2026-09-17).** Squirrel `print`/`printl`/`printt`/`Msg` all funnel through the base-library `print` native at VA `0x6d0b30`, which calls `SQSharedState+0x4350`. That pointer was **not** null as expected - it pointed at the engine's own console sink, which never reaches shadPS4 stdout - so the runtime now *tees* it: logs the text, then forwards to the original so the in-game console still works. Gated on preimages at `0x6d0b30` and `0x6d0b84` (the latter encodes both the `+0x50` and `+0x4350` offsets). This is a data write into the VM's shared state, not a code patch. Script diagnostics are the only channel mods have, and all three remaining failures live behind them.
- **A real match is playable (2026-09-17).** With the client profile repackaged to `1.31.13` so it matches the server, the out-of-sync disconnect is gone and **attrition connects and plays** - the project's first real match, and the milestone Goal 8 was written around. Three separate failures remain, no longer one: attrition **crashes occasionally** (no captured log yet); **fastball hangs on the loading screen** (every stall so far is on `mp_forwardbase_kodai` at the same asset, so gamemode and map are still confounded - run attrition on that map before writing any code); and the **private lobby** raises `ui/menu_private_match.nut#378` `Persistent data not available for client #0`, traced to the engine check `IsPersistentDataAvailable(0)` at client VA `0x2f89f1`. Insecure servers have no masterserver persistence by design; PC fills it server-side via `InitPersistentData()`, so the open question is whether that runs and reaches the PS4 client in time. See [TECHNICAL-NOTES.md](TECHNICAL-NOTES.md).
- **Reached the lobby; teardown fix confirmed; disconnect cause identified (2026-09-17).** A later connect ran the CLIENT lifecycle, loaded `resource/UI/HudVoice.res` and compiled in-game GPU pipelines - the client was rendering `mp_lobby` - then left cleanly: CLIENT VM destroyed with no crash, UI VM recycled, back at the menu. That is the exact path that faulted before the string-ownership fix, so that fix is confirmed. The session ended with an on-screen "out of sync" error, which is `#DISCONNECT_OUT_OF_SYNC` in client.prx and is **a remote-function-call table checksum mismatch**: the server sends `RemoteFunctionCallsChecksum`, the client compares it against its own table checksum at `0x43dea0`/`0x43e64c` and disconnects when they differ. The table depends on which scripts compiled and in what order, and this port compiles a generated `scripts.rson` of its own construction, so a mismatch is expected. **Next: reconcile the generated manifest's script set and ordering with PC Northstar's.**
- **CLIENT lifecycle proven end to end (2026-09-17).** A lobby connect dispatched `ClientCodeCallback_MapSpawn` for the first time on this port: 19 CLIENT Before callbacks (every custom gamemode's `Init`, including `Sh_GamemodeFastball_Init`) then the After set, then `CLIENT lifecycle completed`. Leaving the map then crashed with an access violation in SQString release (client VA `0x69f6e4`), because `RegisterRuntimeConstants` interned its `VANILLA`/`NS_VERSION_*` key strings without writing the shared-state back-pointer at `string+0x18` or taking a reference - `SQString::Create` does neither, and every engine caller does both. Latent since that function was written: the constants table is only released when its VM is destroyed, and no CLIENT VM had ever been created *and* destroyed before. Fixed to match the engine's pattern; **not yet re-tested against a map exit**.
- **First real CLIENT VM (from a live connect):** context 1 was created and the whole CLIENT setup ran - 30 natives registered (including the chat family whose absence caused the earlier "frozen on connect" report), InitScript compiled, deferred natives registered, init complete. It then died on `CLIENT SCRIPT COMPILE ERROR: Redefinition of enumeration "eDiscordGameState"`: the generated manifest still declared each mod's InitScript for CLIENT while `RuntimeVmInit` also compiled it at VM creation, so it compiled twice. Fixed by narrowing that manifest block to `When: "SERVER"` - the manifest may only declare contexts the VM init hook does not cover. `ClientCodeCallback_MapSpawn` was never reached, so CLIENT Before/After dispatch remains unproven and needs another connect.

## Remaining native work, in order

1. **Early engine filesystem integration.** Primary OpenEx and selective ReadFromCache hooks now cover clean-retail UI manifest/script reads. Async reads, assets, disabled-mod cases and priority collisions still need runtime acceptance checks. Do not reintroduce archive baking to bypass this.
2. **Script compile and VM lifecycle.** UI is proven end to end. CLIENT plumbing is written and installed (VM init, context-filtered natives, InitScript + InitScriptCallback, MapSpawn Before/After, destroy) but has **never executed**, because a CLIENT VM is only created on map load. Next step is a map load to exercise it and to find the CLIENT natives that are still missing. SERVER is untouched: `server.prx` is not loaded until a server is hosted and none of its addresses are profiled. No per-frame tick exists either, so the deferred script-call queue drains at the next code callback for that context instead of the next frame; port PC's `CHostState::FrameUpdate` drain point. Preserve compound RunOn expressions rather than silently treating them as UI-only. Do not enable the experiment by default.
3. **PC native API surface.** Mod-list, enable-state persistence, Safe I/O, JSON, `StringToAsset` and the mod-name natives are implemented and gated. **Adapters that accept calls but do nothing:** `NSChatWrite`, `NSChatWriteLine`, `NSChatWriteRaw` and `NSSendMessage` - chat needs `LocalChatWriter` and engine.prx's `ClientSayText` ported. **Still entirely missing:** the SERVER family (`NSBroadcastMessage`, `NSSendMessage` server variant, `NSIsPlayerLocalPlayer`, `NSIsWritingPlayerPersistence`, `NSEarlyWritePlayerPersistenceForLeave`, `NSDisconnectPlayer`, `NSSendClientPrint`, `NSIsDedicated`, `GetUserInfoKV*_Internal`), plus `NSGetCursorPosition`, `NSGetLoadedMapNames` and `NSGetLocalPlayerUID`. ConCommands, ConVar flags and generated KeyValues/assets also need PS4 implementations. Catalog bounds and the small prototype parser are not full PC schema parity; malformed/oversized/unsupported content needs stronger diagnostics. Multiple installed versions, packages/remote mods and live reload remain unsupported.
4. **Platform compatibility.** Move the functionality previously supplied by optional `Northstar.PS4` script workarounds into verified native adapters where appropriate. PC plugin DLLs require separate PS4 implementations. Preserve original mod sources.
5. **Vanilla-archive integration acceptance.** Hash original VPKs before and after a run; show unchanged PC mod folders loading, enabled=false suppressing scripts/files/ConVars/localisation, priority collisions resolving correctly, all VM lifecycle callbacks firing once, and a clean main menu/map load. UI callbacks firing once in order is now shown; the enabled=false, priority-collision and clean menu/map-load parts of this milestone are **not** yet shown. A PRX build or module-tracker success marker alone does not pass this milestone.
6. **Connectivity and hardware.** Atlas/server browser and real PS4 validation follow the loader. The previous server auth rejection and generic dialog-input issue remain open; see the historical notebook.

## Native safety rules

- Never use Windows engine/client offsets on PS4.
- Validate the retail module identity and exact byte preimages before native patches/dereferences; preserve the eboot rollback path and back up installed binaries.
- Keep extracted retail data and generated binaries out of Git.
- Treat emulator and real hardware validation separately.
- Unknown native milestones begin with read-only profiling. A known-crashing injection remains opt-in until verified.
